10 ideas from Stripe's company agent, Kai

Stripe built its own company agent because the hard part wasn't giving people AI. It was giving 10,000+ employees AI that follows how Stripe works. These notes come from Sharadh, an engineering manager on the Kai team, talking with Claire Vo on How I AI.

Tap any idea for the details
  1. 1Ship governance, not just access. The hard part of company-wide AI is copying how the company works: permissions, costs and sensitive data. Build those guardrails so people can just use AI and trust it.Details · quotes

    The real problem was how the company works

    In early 2026 there was a flood of new AI tools. Stripe's question was how to get AI to everyone. The team quickly saw that this wasn't mainly a technical problem.

    "It's not about providing AI, it's about providing the correct governance structures so that everyone can just go use AI and know it'll do the right thing for them." — Sharadh

    Why build instead of buy. Four reasons came up:

    • Governance that fits Stripe's processes: cost, data sensitivity and approvals.
    • Context: the agent knows who the user is, their org and their projects.
    • Security: it runs in the cloud, is always on and sits inside Stripe's security boundaries.
    • Dogfooding: it uses the same infrastructure Stripe uses to build agents for its customers.
    What to do with thisList the rules your company already runs on: who sees what data, who can spend how much, and what needs sign-off. Then check whether an off-the-shelf tool can follow those rules without adding friction.
  2. 2Use projects as a governance layer. A project isn't just a folder of chats. It's where a few experts set the default model, tools, skills and even the agent backend for everyone doing that job.Details · quotes

    Projects tell the agent what you're trying to do

    When a user picks a project, they are telling the agent what job they're doing, and that helps it perform better. Projects range from 5 people to 500.

    The project's owner (its DRI) sets the defaults:

    • Default model, including blocking expensive models when the job doesn't need them.
    • Which skills are in scope. Stripe has about 2,000 skills, and each project limits the set to the relevant ones.
    • Tool policies (see idea 3).
    • A custom agent backend. The People team runs a "super secure version of Kai" with its own back end.
    "We should try to minimize the number of people who have to actively make these choices every day and just it should do the right thing for them." — Sharadh
    "Kai looks like a single product. It really isn't. It's like the icing on top of a multi-layer cake." — Sharadh
  3. 3Set tool rules per project, not per person. Require human approval for risky tools only in sensitive projects, like HR. Asking for approval everywhere teaches people to click "yes" without reading.Details · quotes

    Put the friction only where it's needed

    Someone on the HR team handles sensitive data. You don't want the agent to paste it into a Google Doc every employee can open. But banning all tools for that team goes too far.

    "You really don't want the agent to sort of go rogue and put that sensitive data into some public Google document that all Stripes can access, but you also don't want to tell them, oh, you can't use any tools." — Sharadh

    In the demo, asking Kai to "create a calendar invite for me and Wong tomorrow at 11:00 a.m. Pacific" brought up a human-in-the-loop confirmation. A project can also block a tool outright.

    "If I showed you this every single session for every single tool, eventually you're going to press the wrong button." — Sharadh
    What to do with thisSort your agent's tools by risk: write actions, external sharing and sending messages. Require approval for those per workspace. Keep read-only tools free of approval steps.
  4. 4Give the agent limited context that users control. By default Kai knows who you are and where you sit in the org chart. Users choose whether to connect Drive, Slack and DMs, and can switch them on or off each session.Details

    Start with low-risk context, and let users opt in to the rest

    • Who you are and where you sit in the org chart
    • Basics like the current date and time
    • Your projects, OKRs and recently shipped emails, from Stripe's project system

    Sensitive sources are opt-in. Google Drive, Slack and private messages connect only if you choose to connect them. Sharadh turns his access on and off every session or every day. Others leave everything on because "more context is better."

    Projects add intent on top of identity. The org chart says who you are. The project says what you're doing right now.

  5. 5Get your data layer ready for agents with a set lookup order. Teach the agent to try existing reports first, then the trusted analytics tables, then the raw data catalog. Make the warehouse sturdy, because "when in doubt an agent will just brute force it."Details · quotes

    A lookup order that data scientists wrote

    Dashboards are the first agent almost every company builds. At Stripe, "literally everyone" makes them with Kai. Stripe's data scientists wrote the lookup order into an "ask data" skill:

    1. Existing reports: reuse reports, dashboards and the queries behind them.
    2. Trusted analytics tables: the curated home of key metrics.
    3. Data catalog: search rated, high-quality datasets and write a new query only as a last resort.
    "These investments were made for humans but have held up really well for agents because… they can answer the question, but they have no idea if it was the right query or the right table." — Sharadh

    The warehouse has to handle agent traffic. Stripe made its Trino query layer sturdy long before agents arrived. That's why agents can "slam it like crazy" without bringing it down.

    "Double the size of your DevX team, double the size of your data team… Good for humans, good for agents." — Claire Vo
  6. 6Expect agents to make every existing failure worse. At Stripe, agents nearly took down core systems. Label agent traffic so your systems can prioritize it and drop it first under load.Details · quotes

    Agents make existing problems bigger

    "It turns out that agents just like dial up all your failure modes… it just multiplies the amplitude of problems you can get." — Sharadh

    Stripe had "agents that went rogue" and agents that "may have almost taken down core systems." The team caught them in time and made those systems sturdier.

    Agent identity is the fix. Stripe is working on marking each request as coming from an agent, along with what the agent is trying to do. Systems can then decide which requests come first and drop agent traffic when under stress. Sharadh said this isn't solved yet.

    What to do with thisTag every agent call with who is calling and why. Treat agent traffic as its own group in rate limits. Test what happens when an agent goes rogue against your most critical systems.
  7. 7Give everyone a secure sandbox, and keep improving the same artifacts. A private cloud workspace for each session lets non-engineers have the agent write code for their own data work. Dashboards get refined over many turns instead of rebuilt.Details · quotes

    A sandbox lets anyone build small apps for their own work

    Kai runs in the cloud, so sessions can't "eat each other." The agent has tools to send data into the sandbox, run code there and pull results out. Users never need to know the sandbox exists.

    Every workflow is different. A dashboard for every need would mean "a gazillion dashboards" nobody can maintain. Instead, people have the agent build small apps for their own job.

    "The fact that they have a sandbox that anybody regardless whether they're an engineer or not can get the agent to write code for them and do whatever the heck they want with the data. It's really powerful." — Sharadh

    Artifacts stick around. In the demo, a follow-up prompt added a new section to the same dashboard. That uses fewer tokens than regenerating it. Some conversations run for hundreds of turns over several weeks. Sharadh now makes a dashboard for every meeting he runs.

  8. 8Turn a good session into a skill you can share. A built-in skill creator packages what worked into a repeatable workflow. Anyone can keep the skill private, share it with a team or publish it company-wide.Details · quotes

    How a one-off becomes a workflow you trust

    1. Kai writes the skill from the session, in an open skill format other agent tools can also use.
    2. It fills in a description of when to use the skill. That text is how Kai finds the skill later.
    3. The author keeps it private, shares it with a team space or publishes it.
    4. A simple editor lets anyone test and adjust the draft.

    The payoff: "Give me the latest Kai adoption dashboard" picked up the brand-new skill automatically.

    "You can just go in and start using Kai and it knows what to do. This is how it knows." — Sharadh

    Finding the right skill is harder at work than in code. A coding agent can use folder structure to find skills. At work there's no such structure, and one task often touches five systems.

  9. 9Maintain the skill library like a product. With about 2,000 skills, Stripe tracks usage and suggests improvements to keep quality up. Too many unrelated skills fill up the agent's context, so having fewer is part of quality.Details · table · quotes

    Most skills are used by a few people

    Anyone can publish a shared skill, so keeping quality up is the platform's job. Kai automatically suggests improvements to every skill author.

    GroupAbout how manyUsed by
    Core~50Used heavily every day across the company
    Long tail~100–150Parts of the org chart
    NicheMany moreTeams of two or three people

    Usage data shows which skills to add to everyone's default set and which narrow ones to take out so they stop crowding the agent's context.

    "You can't separate quality and quantity… the more unrelated context you throw into the AI, the less good your results become." — Sharadh

    Claire's add-on: a retirement rule. If nobody uses a skill for about 30 days, the owner gets a notice. If they don't respond, it's marked for retirement and deleted about two weeks later.

  10. 10Ship a cheap first version, pilot it with an eager team, then demo it to everyone. Kai's first version took 1.5 engineers two weeks. A pilot with the go-to-market team proved it worked, and a company-wide demo drove the big jump in use.Details · table · quotes

    A demo convinced people faster than explaining

    It was hard to argue for a company agent when coding agents already seemed powerful. Once people could see the first version, the questions answered themselves.

    StageTeamUsers
    First version (v0)~1.5 engineers, 2 weeksThe builders
    Pilot (~1 month)2.5–3 people200–300, mostly go-to-market
    After company demoFewer than 10 core10,000+ weekly · 86%+ of the company

    Pick a pilot team that's eager, not just willing. Stripe's go-to-market team was looking for any edge to reach more customers.

    A small team can do this with help. Coding agents, Stripe's in-house developer tools and its existing infrastructure did much of the work.

    "It sounds like we figured this all out. We absolutely haven't… we are in the earliest parts of this journey." — Sharadh

TermMeaning here
KaiStripe's internal company agent, its "company brain." The spelling comes from the auto-captions.
HarnessThe software around a model, such as tools, skills and a sandbox, that turns the model into an agent
ToolAn action the agent can take, such as running a query or creating an invite
SkillA packaged set of instructions for one kind of task, loaded when it's relevant
Skill routingHow the agent picks the right skill, based on each skill's description
ProjectKai's way of setting rules for a group: default model, skills, tool rules and an optional custom backend
DRIDirectly responsible individual, the person who sets up a project
Tool policyA rule in a project that allows a tool, blocks it or requires approval
Human in the loopThe agent pauses for a person to confirm before it acts
SandboxA private cloud workspace for each session, where the agent runs code
ArtifactA lasting output, like a dashboard, that gets improved over many turns
Last-mile dataAnalysis specific to one workflow that no standard dashboard covers
HubbleStripe's internal tool for querying data
